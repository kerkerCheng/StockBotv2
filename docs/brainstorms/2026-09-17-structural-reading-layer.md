# 瓶頸性不是一條邊——結構讀圖層（2026-09-17）

> **緣起（使用者原話）：** 「我也確實想強調瓶頸性可能不是一個太單一的邊可以替代。像這次的來回，
> 或是之後我覺得很多事情可能都是要來回的查找圖才看得出來的。我希望 leverage LLM 思考的能力，
> 思考怎麼樣才是 A B 真正的答案，並不是單純查圖。」
>
> **性質：** 設計提案 ＋ 一個已經跑過的實例。**尚未實作**，要使用者決定。

## 1. 這個觀察是對的，而且今天有一個現成的證據

`substitutability` 是**掛在單一條邊上的純量**。而「CW DFB laser 是不是瓶頸」這一題的答案，
今天是由**四個不同角度的邊**湊出來的——沒有任何一條邊自己說得出來：

| 角度 | 圖裡的邊 | 值 | 它單獨說了什麼 | 它單獨**沒**說什麼 |
|---|---|---|---|---|
| **需求側** | `tech:pluggable_transceiver` depends_on `tech:cw_dfb_laser` | **sub 4** | 這個技術繞不掉 | 誰能收到租金 |
| **供給側** | 6 家 supplies_to `tech:cw_dfb_laser` | COHR 4–5／LITE 3／聯亞 3／華星光 2／Sivers 2／全新 2 | 沒有一家獨佔 | 這層到底卡不卡 |
| **下一層** | `tech:cw_dfb_laser` depends_on `mat:inp_substrate` | **sub 5** | **更卡的在下面** | 誰在那一層 |
| **反向路徑** | `prod:blazar` competes_with `tech:cw_dfb_laser` | — | 有替代路線在競爭 | 它有多接近 |

**四條邊放在一起才有答案：CW DFB laser 是一個「技術繞不掉、但供應層競爭、而且更卡的在它下游」的位置。**
——那正好是 **B 型（量的賭注）** 的定義，不是 A 型（護城河）。

而且它同時回答了前四輪研究的困惑：**聯亞 3、華星光 2、全新 2、穩懋 2、Sivers 2 不是研究不夠，
是在正確地測量一個競爭供應層。** 單看任何一條邊都看不出這件事。

## 2. 為什麼現行架構看不到——不是圖缺，是沒有人把邊組合起來

三件事各自都不是 bug，疊起來就是這個缺口：

1. **`rank_bottlenecks()` 一次只看一條邊。** 它讀 `src` 以 `co:` 開頭的向下邊，
   所以 `tech:pluggable_transceiver depends_on tech:cw_dfb_laser`（sub 4）**結構上永遠讀不到**。
2. **排序鍵刻意不是加權綜合分數**（註解逐字），所以它**本來就不打算**把多條邊合成一個數字——
   那是正確的設計，不該改。
3. **於是「把四條邊讀在一起」這件事沒有任何 owner。** 今天它只在互動 session 裡臨時發生，
   做完就散了——這一輪的 CW laser 分析如果沒寫下來，明天就不存在。

⚠ **這是同一個形狀的第二與第三個實例**（L17：第二個實例出現就該泛化）：
- 第一個：[589] 的 `constrained_by` 在圖裡，但 `UPSTREAM_RELATIONS` 沒收它
- 第二個：技術層的 sub 在圖裡，但排序只讀公司層的邊
- **共同形狀：圖記了，消費端沒讀。**

## 3. 提案：加一層「結構讀圖」，但它**不准 gate 任何東西**

**分工要先講清楚，否則會變成把 LLM 放進權限路徑（L15 明禁）：**

| 層 | 誰做 | 可不可以決定去留 |
|---|---|---|
| 圖（事實與 provenance） | 確定性 loader ＋ 人工 gate | — |
| 排序（`rank_bottlenecks`） | 確定性，零 LLM | 可以（現行門檻），**不動** |
| **結構讀圖（新）** | **LLM 推理** | **不可以**——它只寫下讀到什麼，不濾、不排、不給尺寸 |
| 賭注／Abstention | 人（或 LLM 起草、人確認） | 不可以 |

**「LLM 可以解析與提議，不可以授權」（L15-2）** 在這裡的具體意思是：
結構讀圖產出的是一段**可稽核的文字紀錄**（append-only，帶讀了哪幾條邊），
它是**寫賭注的輸入**，不是一個新的過濾器。

### 五個角度是封閉清單，不是自由發揮

⚠ 清單直接來自**今天真的問出答案的那四個角度**，加上一個本來就有的可達性檢查——
不是憑空設計的。每個角度都對應一條可機械執行的圖查詢：

1. **需求側**：誰 `depends_on` / `is_component_of` 它？那些邊的 `substitutability` 多少？
   → 回答「這個位置繞不繞得過」
2. **供給側**：誰 `supplies_to` 它？sub 的**分布**長什麼樣？
   → 回答「有沒有人獨佔」——**分布才是答案，單一最大值不是**
3. **下一層**：它自己 `depends_on` 什麼？那條邊的 sub 多少？
   → 回答「更卡的是不是在下面」
4. **反向路徑**：有沒有 `competes_with` / `constrained_by` 指向它？
   → 回答「有沒有替代路線」（這也是 disproof 的來源）
5. **需求錨可達性**：走不走得到有人花錢的地方？
   → 已經有的檢查，但要納入同一份讀圖紀錄

### 產出：**這一檔是 A 還是 B**，以及憑什麼

從 CW laser 那個實例裡浮出來的判準（**仍未量測，所以只寫不擋**）：

| 需求側 sub | 供給側分布 | 讀成 |
|---|---|---|
| 高（≥4） | 有人 4–5 且明顯高於其他 | **A：護城河賭注** |
| 高（≥4） | 大家都 2–3 | **B：量的賭注** |
| 低（≤3） | 任意 | **都不是**——這個位置本來就不卡 |
| 任意 | 任意，**但有強 counter-path** | 兩者都要打折，且 counter-path 就是 disproof |

⚠ 這張表**不得**被寫成程式去自動分類——它是給讀的人的判準，
而 INV-5（未量測的機制不得享有默認信任）在這裡的意思是：
**先讓它以文字形式產出幾十份，看它講得準不準，再談要不要機械化。**

## 4. 這一層正好補上今天量到的那個缺口

籃子 16 檔裡 **15 檔卡在 `no_bet`**。為什麼沒人寫賭注？
因為**寫一個賭注需要的正是這種多邊推理**——你得先知道「它是 A 還是 B、卡在哪一層、
誰在競爭它」，才寫得出「我賭什麼、值多少、錯了怎麼認」。

今天從圖到賭注之間是空的：**圖給你一堆單邊事實，賭注要你給一個結構判斷，中間沒有東西。**
結構讀圖層就是那個中間物。

## 5. 明確不做

- **不改 `substitutability` 的定義、量表或門檻。** 它回答的是單一條邊的問題，那個問題本身沒錯。
- **不做多邊加權綜合分數。** 排序鍵註解逐字禁止，而且會讓人看不出是哪一軸驅動結果。
- **不讓 LLM 的讀圖結果 gate 任何東西**——不濾候選、不改排序、不給尺寸。
- **不先機械化那張 A/B 判準表**——先產出、先看準不準（INV-5：先量測後放閘）。

## 6. 要使用者決定

**Q4｜要不要做「結構讀圖」這一層？**
- **A（建議）**：做，但**先做最小版**——一個 `python -m query.structure <node>` 把五個角度的邊
  一次查出來排版好（**零 LLM，純查詢**），LLM 的推理留在互動 session 裡用它產出讀圖紀錄。
  理由：先把「來回查圖」這件事從十幾次手打查詢變成一條命令，**成本最低、且立刻可用**；
  要不要自動化推理，等有幾十份讀圖紀錄再看。
- B：直接做完整版（自動跑 LLM 產生讀圖紀錄並落地）。
- C：不做，維持互動 session 臨時查。

⚠ 判準：**你要的是「不用每次重新想」還是「不用每次重新查」？**
今天的 CW laser 分析裡，重新想的部分約 20%，重新查的部分約 80%——所以 A 先解掉大頭。

**Q5｜這一層的產出要不要落地成 append-only 紀錄？**
- **A（建議）**：要。否則每次分析做完就散了，下次還要重來——今天這份如果沒寫，明天就不存在。
  落點沿用既有的 `alpha/narrative`（append-only ledger，已經是「文字由研究 session 寫、
  數字由 authority 填」的設計）。
- B：不落地，只當互動輸出。
