## 2. 三個產出（都給人讀，不 gate、不排序、不給尺寸）

1. **傳導時差表**（AI 這一波）：錨的消息出來之後，每一層的三個時鐘——證據（帶日期的一手事實）、數字（營收與毛利）、價格（起漲、翻倍、十倍、高點）——各自什麼時候動。
2. **結尾標記表**（舊劇本＋這一波的現況）：過去的循環結束前與中段急跌前，各出現過哪些可觀察的標記；同一組標記在 AI 各層今天亮不亮。
3. **每層對照表**（兩邊都做）：同一層裡，起漲前就看得到的結構事實（客戶掏錢、客戶端印證、合格狀態、供給時鐘）與後來誰吃到，並排。

消化端怎麼用（層級反證模板、賭注句、同一筆賭注內的預設表達）是 §9 第 4 段，逐項另議。

## 3. 確認型與描述型的界線（本稿最重要的一節）

| | 是什麼 | 能說什麼 | 不能說什麼 |
|---|---|---|---|
| **確認型**：只有 H16（§4） | 全台股、零 LLM、定義與判讀線先 commit、結果窗在掃描看過的期間之前 | 「大跌當時的機械標記分得出／分不出中段與結束」 | 超出台股、月頻、2015–2021 的任何外推 |
| **描述型**：§5、§6 的三張表 | 人挑的錨與清單、已看過的股價、小樣本 | 「這幾段裡出現過這個順序／這個標記」；每一格指得回逐字引文與日期 | 「這個特徵有效」「這個標記會預測結束」 |

- 描述型的發現要變成依據，只有兩條路：①寫成前向假說進 Phase 7 的帳、往後量；②寫成層級的反證或加碼條件、登記 watch（觸及只提醒）。**不得直接變成排序、門檻或預設。**
- v1 的 HP1–HP4 全部降為「對照表的欄」，不做檢定、不寫支持或削弱。理由：方法論審查的檢定力推算（20 段 × 6 家只看得到翻倍率約三倍的差）、
  這一波已被掃描開封、舊劇本的贏家是公開常識。
- 描述型也守紀律：特徵與標記的定義在抽取前凍結；看到資料後才想到的標記一律標「事後」，不與凍結的並列。

## 4. 第 1a 段：機械回放 H16——大跌當時，分不分得出「中段」與「結束」（預先登記草稿）

不需要回放語料、不用模型；與 H11–H14 同一種東西，登記在 `docs/reports/phase7/registration.md`，量在追蹤表的基準率回放那一層（D3）。

- **一句話**：一檔股票漲過三倍之後第一次自高點回落四成，那個月當下已公布的營收、存貨、毛利率、合約負債、同節點廣度，分得出它之後 18 個月會不會再創高。
- **母體與期間**：全台股上市櫃；事件月 **2015-01～2021-03**（結果窗最晚到 2022-09，早於 AI 掃描看過的 2022-10 起）。
- **事件**：月收盤自過去 36 個月內最低月收盤起算曾達 ≥ 3 倍；之後第一次出現月收盤 ≤ 0.6 × 這段漲勢的最高月收盤，那個月＝事件月 t。
  同一檔同一段漲勢只記一次（要再創新高並重新滿足才記下一次）。
- **結果**（標記凍結之後才算）：主量＝t 之後 18 個月內月收盤是否曾 ≥ 事件前高點（是＝中段，否＝結束）。另印 t 起 12 個月報酬、之後 12 個月內再跌 30% 的比例。
- **標記**（只用 t 當月底已可知的資料：月營收到 t−1 月、季報照法定期限；每個先寫預期方向）：

| # | 標記（成立＝「壞」） | 預期 |
|---|---|---|
| M1 | 最近三個月營收年增的平均 ≤ 0，或低於再前三個月的平均（動能轉弱） | 壞的那組「結束」比例較高 |
| M2 | 最近一季存貨天數較去年同季上升 ≥ 20% | 同上 |
| M3 | 最近一季毛利率比過去八季最高點低 ≥ 3 個百分點 | 同上 |
| M4 | 最近一季合約負債較前一季下降 ≥ 20%（只收合約負債 ≥ 單季營收 2% 的公司） | 同上 |
| M5 | 同一櫃買節點成員裡，最近三個月營收年增為正的比例 < 50% | 同上 |

- **判讀線**（每個標記各判）：支持＝兩組各 n ≥ 100、「結束」比例的差 ≥ 10 個百分點且方向如預期、單尾檢定 p ≤ 0.01（五個標記的 Bonferroni）、
  前後兩段（2015–2017、2018–2021-03）同向；削弱＝過 n 門檻而差 < 5 個百分點或方向相反；其間寫「不確定」；n 不足寫「不足」。
- **後果（先寫定）**：只進假說帳，不改任何 filter、候選狀態、排序。五個全削弱 →「大跌當時的財務數字分不出中段與結束」，結尾標記只剩文件型的（§6）；
  有支持的 → 它可以成為層級反證模板的候選（§9 第 4 段另議）。一次判讀，不加標記重試；要加得另開登記、用沒看過的期間。
- **已知偏差**：存活者（之後下市的多半是「結束」，取不到價格會高估「中段」——逐列數出來）；台股、月頻；節點是今天的版本；2020–2021 多頭占事件多數。
- **請審查者定**：事件門檻（3 倍／四成）、結果窗（18 個月）、M1–M5 的門檻值、檢定方法。

## 5. AI 這一波（描述）

### 5.1 錨與錨的時鐘
錨＝AI 資料中心資本支出。時鐘用既有的需求錨序列（`config/demand_anchor_series.json`、`alpha/demand_anchor.py`：SEC 申報值、可知日＝申報日），
加上買家財報裡帶日期的資本支出口徑（事件表）。不設單一 T0。

### 5.2 層清單（照物料清單，不照誰漲）
- 來源兩個，取聯集：①既有的系統拆解研究地圖（`skills/system-decompose` 的產出；它們寫於本稿之前）；②正式圖上有路徑連到 AI 需求錨的層節點。
- 掃描之後才注意到的層（清單上沒有、卻出現在十倍股裡）**照收但標「事後」**，在三張表裡分開列。
- 每一層在劇本登記表凍結：層的節點 id、上下游各一到兩個固定節點、成員名單與每一家的名單來源。

### 5.3 成員（贏的輸的都要在）
- 台股：櫃買節點＋主要產品關鍵字當候選 → **T 前已公布的最近一份年報**，該產品線占營收 ≥ 30% 才算（另印 20%、50% 敏感度；分不出產品別的不收、計數）。
- 海外：名冊上的＋層成員 **≤ T 的文件**點名的同業；文件用 web search 補（規則見 §8.2）。
- 名單面的存活者：每層印「T 當月月營收頁有、同大類、今天不在任何節點」的家數當上界。

### 5.4 三個時鐘與層的 T
- **價格鐘**（機械）：層成員等權的月線；起漲月沿用 `alpha/detective_backtest.py::rally_starts` 的定義搬到月頻；另記每家第一次達 2／5／10 倍的月、高點月。
- **數字鐘**（機械）：月營收年增、單季毛利率、合約負債、存貨天數、資本支出。
- **證據鐘**（抽取）：事件表與邊的首見日，分發布者（自己／客戶端／第三方）。
- **層的 T**＝層等權起漲月的前一個月底；對照表的結構事實一律只用發布日 ≤ T 的。這個 T 用了股價——在描述型裡可以，並且寫明。

## 7. 回放語料與架構（落實第一輪架構審查）

- **落點（A-B2、D2）**：`library/replay/raw/` 預設 gitignore，只追蹤清單（網址、sha256、大小、抓取日、發布日與定日方法、`storage_permission`）；
  抽取檔每份帶 `storage_permission`／`permission_basis`，未宣告不追蹤；測試斷言 `git ls-files library/replay/raw` 只有清單。試點不做冷備份。
- **對正式系統單向（A-S1）**：除 `replay/` 與它的測試外，全 repo 的 .py 不得 import `replay`（白名單測試）；正式路徑的 .py 不得出現 `library/replay` 路徑字串；
  不為回放開新的出處前綴。**出口只有兩個**：晉升（從原始檔重走正式抽取與入圖 gate，回放抽取只當線索、不搬檔；A-S6）與回放報告（三張表）。
  劇本要寫進層說明或敘事，得先把依據的文件晉升。
- **身分（A-B1、D1）**：舊公司與層裡的輸家進同一份名冊、帶「回放專用」宣告；`IdentityRegistry` 現行讀法預設不含，另開含回放的讀法；
  仍走 registry batch、一段一號，但回放專用條目跳過 lead 重算與 Engine C 歷史補抓。測試：把一家回放專用台股加進名冊副本，
  MOPS 監看清單、每日物化的宇宙、共用寫法集合、lead 實體重算四處逐項不變。
- **現行題材的公司兩邊都有**：AI 這一波的成員多半已在正式圖上，但正式庫的選文是研究驅動的（贏家文件多）。**三張表只從回放語料算**；
  正式庫裡符合選文規則（型別、窗）的既有文件可以引用同一份原始檔，但收不收照回放的規則，不照「手上剛好有」。
- **事件表（A-B3、A-S2）**：sidecar `<doc_id>.events.json`，引用同一份抽取的 `sources[].id`，回放自己的 JSON Schema 驗；主檔原樣過正式 validator。
  事件字彙沿用 `config/structural_event_kinds.json`（`capacity_expansion`、`price_move`、`qualification`、`design_win`…），只新增 `capital_commitment` 一列並登記；
  不設 `second_source`（由邊推導）。事件裡的數量、幅度、預定開出日是時變觀測——它們正式的家是 A2 或 dated Claim，不是邊屬性。
- **節點身分（A-B4、M-B4d）**：每段的層節點在登記表凍結；抽取提示只給這份清單與名冊公司（`extract.py` 加注入點），不讀 Neo4j；特徵只數指向登記表節點的邊。
- **不另立定義（A-S2）**：「非自報」「關係人」「as-of」沿用 `query.origin_resolution` 與 `project_assertions_as_of`，回放只寫 JSON→rows 的 adapter；
  `collapse_assertions` 一律傳空的 resolutions。
- **定日（A-S7）**：`published_at` 沿用 `loader/source_dating.py` 的定日方法、逐份記方法；模型從內文讀出的日期不算。
- **守門清單（A-S5）**：新套件同一個 change 加進四份寫死的清單（層分離、無 LLM API、殭屍 grep、ROADMAP 引用）；回放的提示放 `prompts/` 底下讓字表守門掃得到；不用「籃子」。
- **規則版本（A-S9）**：每段記選案、選文、抽取提示、特徵的版本；同一張表只收同一版本的段，改版＝舊段重跑或分表。

## 8. 選文、抽取、抽查（落實第一輪方法論審查）

### 8.1 只用 ≤ T 的四道防呆（M-B4）
①特徵在 assertion 與事件層級過濾發布日，不在邊層級——變異測試：一條邊有 T 前的自報與 T 後的客戶端文件，「客戶端印證」必須是 0。
②對手方與海外同業名單只由 ≤ T 的文件產生；T 後才出現的另成一組，只進傳導時差表。③文件上限分 T 前、T 後各自計，T 前優先。④提示不帶今天的圖（§7）。

### 8.2 選文
- 型別與窗：層的 T 前 18 個月到後 24 個月（舊劇本到結束後 12 個月）的年報、法說簡報、歷史重訊、財報附註；美股 10-K／10-Q／8-K＋EX-99。
  年報只取章節白名單（先定、不看內容調）。照規則抓、不手挑；抓不到的逐家逐型別計數。
- **海外用 web search（J6、A-S4、M-S5）**：互動工具沿用新聞雷達的搜尋收集——查詢字串由程式照固定模板組、網址由程式從搜尋結果收；每家的官方網域在登記表記一格、人確認一次；
  只收官方網域或交易所公告系統上的文件；發布日推不出就排除並計數；每家每年有上限；全部登記。
  **搜尋不可重現、只剩還活著的網站**——所以表裡凡是靠海外文件的格都分「台股（機械）／海外（搜尋）」兩欄並附覆蓋率，覆蓋率低的段那一格寫「量不到」。

### 8.3 抽取與抽查（M-S1、M-S2）
- 執行：`claude -p` 零工具批次，argv 只來自 `crons/llm_step.py`；設定住 `config/replay.json`；每次呼叫後讀額度、過線就停、可續跑；只寫忽略的回放路徑，遇 daily 寫入窗暫停。
  sandbox impact review 五步放第 1b 段同一個 change，不新增 rule、不進 daily（A-S3）。
- 逐字引文存在與否由程式**全檢**；進三張表的每一條事實由主 session 對原文核；30 份文件獨立重抽一次量一致率；
  另印「每千字抽出事實數」在最後贏家與輸家之間的差（模型記得誰贏時，抽得勤不勤的診斷）。
- 計數型的格（印證邊數、事件數）一律並印該公司 ≤ T 的文件數；兩組文件數中位數比 > 1.5 時那一格標「文件量混淆」。加一個負控制（它當付款方的 `capital_commitment` 件數）。
- 抽取清單（每份 sha256、模型、提示版本）在出表前凍結；之後的更正只能追加新版，兩版並列（A-S6）。

## 13. 請第二輪審查者攻擊的問題

**方法論**
1. H16 的事件、結果、標記與判讀線：哪裡會偷看未來、哪裡會把雜訊判成支持、存活者偏差會把結論推向哪一邊？請給具體門檻與檢定力推算。

3. 層的 T 用股價定、成員用 30% 營收比重定、結束與中段用價格標——哪一個在描述型裡仍然會做出假規律（例如把「漲最多」做成「結構最好」）？
4. 舊劇本九段是憑記憶提的：這份清單對「怎麼結束」會有什麼系統性的偏？缺哪一型的結尾？
5. 結尾標記 E1–E8：哪些其實是同一件事的兩種量法；哪些在回落起點的前一個月根本還看不到（價格領先基本面）？
6. 第一輪 M-B1～B4、M-S1～S8 在 v2 有沒有真的落實，哪一條只是換了位置？

**架構邊界**
1. 現行題材的公司同時在正式圖與回放語料：§7 的規則夠不夠？哪一條既有的測試或計數會因此改變？
2. 名冊「回放專用」宣告、sidecar 事件表、提示注入點、守門清單——逐項去 repo 找反例：v2 的寫法實際做下去會撞到什麼？
3. 1a 掛 Phase 7、其餘開 Phase 8、同一個 commit 改 phase-run：流程上有沒有洞？§9 的驗收欄合不合 G10？
4. 第一輪 A-B1～B5、A-S1～S9 在 v2 有沒有真的落實？

**決策效用**
1. 使用者要在急跌當下決定買不買、買哪幾檔：這份設計最早什麼時候能給他第一個有用的東西？那個東西會不會誤導他？
2. 三個產出裡，哪一個對「從 22 檔可開挑幾檔」最沒有幫助、可以砍或延後？有沒有更小、更快、同樣誠實的第一個產出？
3. 這份設計在哪裡重演了 G3 之前的失敗（研究做很多、消化端沒變）？第 4 段排在最後，是審慎還是偏差？
