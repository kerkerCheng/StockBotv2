# System Decompose Skill（v1）

## 定位一句話

**選一台實體機器，問「要造出它，世上必須存在哪些東西」，再回頭看我們的圖漏了哪一層。**

---

## 為什麼需要它：排序解決不了發現

現行迴路是：

```
圖 → rank_bottlenecks → chokepoint_tickers → pq1 排序 → 研究什麼 → 圖
```

整條線上**候選的來源都是圖自己**。`coverage_gaps` 也只能從既有節點往回看，而那些節點是
從我們讀過的文件掉出來的。**沒有任何一環會提出一個我們從沒聽過的瓶頸。**

本 skill 把箭頭反過來：**圖從「候選的來源」降級為「已知清單」**，只在最後一步用來分類結果。

⚠ **誠實的限制：迴路只斷了一半。** 「選哪個系統」仍是人的決定，且 LLM 列層來自訓練資料、
有自己的覆蓋偏差。它斷的是「圖 → 候選 → 圖」這個看不見的棘輪，不是所有迴路。
剩下那個（選題）至少是明擺著、每次都要寫下來的人為決定——**所以選題理由必須留在輸出裡**。

---

## Step 1 — 選定系統：必須是「一台實體」，不是一個類別

| ✅ 可以拆 | ❌ 不能拆 |
|---|---|
| NVIDIA GB300 NVL72 機櫃 | 「AI 資料中心」 |
| Google TPU v7 pod | 「加速運算」 |
| Figure 03 / Unitree G1 | 「人形機器人」 |
| 800G/1.6T 光收發模組 | 「光通訊」 |

**判準：你能不能指著一個東西說「這一台」。** 類別會拆成更多類別，永遠拆不到底；
實體會拆成零件。**這是整個 SOP 最容易失敗、也最便宜的一步**——選錯了，後面全是空轉。

選題**必須由使用者給**（或使用者先前點過、由週掃執行的積壓題）。理由見上方「誠實的限制」：
若讓排程自己挑，它只能從圖和 leads 裡挑，等於原地繞回。

輸出必須記下**選題理由**（使用者的原話最好）。

## Step 2 — 列層：來源是一手規格，**禁止查我們自己的圖**

可用來源：vendor spec sheet／datasheet、teardown、OCP／OFC／ECOC 論文、專利、
標準文件（OIF、IEEE）、法說會中的架構描述。

**這一步刻意不看圖**，否則會退化成「把已知的東西再列一次」。

⚠ **L6 Gap 4 在這一步最危險**（LLM 從類別詞推斷出具體實體，是最常見的幻覺型態）。規則：

- **層的名字可以是通用的**（「外部雷射源」「retimer」「液冷分水器」）——這是結構描述
- **任何具體公司名／型號必須在一手文件裡逐字出現**，不得由「這一層應該是 XX 做的吧」產生
- 想不出誰做某一層，就寫「未知」——**那正是要產出的研究題目**

## Step 3 — 每層問三個瓶頸題

1. **幾家能做？**
2. **換掉要多久？**（**合格週期 qualification，不是交貨週期 delivery**——兩者混用會讓
   「難替代 vs 換掉要多久」這個區分失效，見 ROADMAP 未排程該項）
3. **有沒有客戶端資本承諾？**（誰付錢給誰——四維度裡最難偽造的一項）

**答不出來就標「未知」，不准猜。** 未知本身就是下一步的研究題目；猜了反而把題目藏起來。

## Step 4 — **這時候才**對照圖

```bash
python -m query.coverage_gaps        # 既有 chokepoint 節點的覆蓋狀態
python -m query.bottleneck           # 既有邊的排序（確認該層是否已被建模）
```

⚠ 公司 ID 不要憑公司名猜，唯一權威是 `config/company_identity.json`／`identity.registry`。

三堆分類：

| 結果 | 意義 | 下一步 |
|---|---|---|
| 有節點、有供應商 | ✅ 已覆蓋 | 無 |
| 有節點、零供應商 | 🟡 `coverage_gaps` 已在報 | 找誰供應它 → pq1 |
| **圖裡根本沒這個節點** | 🔴🔴 **未知層** | 建節點＋找供應商 → pq1 |

**第三格是本 skill 存在的全部理由。** 系統裡沒有其他機制能產出它。

## Step 5 — 產出研究題目（進 pq1，不是給人點頭的清單）

只有第二、三堆產出題目。每題附上
[`config/lead_classification.json`](../../config/lead_classification.json) 的
`decision_impact` 分類（未知層多半是 `候選集合`），與 pq1 排序共用同一套字彙。

題目形態：「誰供應 `tech:X`？」「`tech:X` 有幾家能做、換掉要多久？」

## Step 6 — 留 receipt

選了哪個系統、為什麼、一手來源清單與各自 tier、拆出幾層、三堆各幾個。
**這是選題的稽核軌跡**，也是日後回答「這個機制到底有沒有用」的唯一依據。

---

## 三條不可逾越

1. **完全不碰圖。** 產出是**研究地圖，不是知識**。任何一層要進圖，走原本的
   `library/raw/ → extract → validate → RA → pq2 核准` 路徑，一步都不省。
2. **不提高任何 evidence tier。** 拆解本身通常是 tier 3–4（推論、二手規格），
   價值在指路不在佐證。
3. **「這一層存在」本身也是 claim。** 只由 LLM 記憶列出的層就是 tier 4，必須標成 tier 4。
   **這條最容易鬆手**——拆解的輸出看起來很結構化，很像事實。

⚠ **raw 是這條紀律的執行力，不只是慣例**：層要進圖就必須有 raw 撐著。所以
「層本身也是 claim」不用靠自律——**沒有 raw 的層連進圖的入口都摸不到**。

## 輸出格式

```
系統：<一台實體>          選題理由：<使用者原話>          日期：<YYYY-MM-DD>
一手來源：<逐條列 URL／文件與各自 tier；記憶推論的部分明標 tier 4>

| 層 | 幾家能做 | 換掉要多久（合格） | 客戶資本承諾 | 圖中狀態 | 研究題目 | 答案會改變什麼 |
|---|---|---|---|---|---|---|
| 外部雷射源 | 未知 | 未知 | NVIDIA→COHR 20 億 | ✅ 已覆蓋 | — | — |
| scale-up CPO | 未知 | 未知 | 未知 | 🟡 零供應商 | 誰供應它 | 候選集合 |
| <某一層> | 未知 | 未知 | 未知 | 🔴 圖裡沒有 | 建節點＋找供應商 | 候選集合 |

收斂：拆出 N 層｜✅ 已覆蓋 X｜🟡 零供應商 Y｜🔴 未知層 Z
```

**最後一行的 `Z` 是這個機制唯一的成績單。**

⚠ **反向的自我欺騙要先堵起來：** 「拆完發現全部都已覆蓋」聽起來像好消息，但以目前實況
（`substitutability` 覆蓋率約 16%、40+ 個零供應商節點），**首次拆解若 `Z = 0`，正確結論是
「拆得太粗或選錯系統」，不是「我們覆蓋完整」。**

**`Z` 長期為 0 就代表這個 skill 是裝飾品，該砍掉**（L14：未經量測的機制不得享有默認信任）。

## 節奏：人給節奏，週掃只保證不歸零

| | 角色 |
|---|---|
| **使用者（隨時）** | **選題並執行——主路徑** |
| **本 skill** | 兩邊共用的 SOP |
| **週掃** | ①執行使用者點過但未做的積壓題 ②提醒「距上次拆解 N 天」③從 leads 提名候選系統**給使用者挑，不自己決定** |

週掃已經在做 topic discovery，拆解是最正宗的 topic discovery；它的固定節奏保證這件事
不會被每天數十則的 harvest 餓死。搭週掃報告便車留檔，**不新增任何檔案格式**。

---

## 不做什麼

- **不留檔。** 輸出只出現在 session（或搭週掃報告便車）。判準：**這個產物如果不存，
  明天會有誰真的少了東西？** 覆蓋狀態 `coverage_gaps` 一行就重算得到；層的結構該進圖；
  研究題目該進 pq1；三者都有既有的家。
- **不新增 lifecycle、不新增 cron、不新增 config、不佔 pq2 編號。**
- 若跑過兩三次後發現真的在重複推導同一件事，**那時才加最小持久化**——不在跑之前先蓋倉庫。

## 第一個目標：CPO stack（成本最低）

`coverage_gaps` 的 🔴 清單裡有一整群是**同一次沒做完的拆解殘骸**——
`tech:scale_up_cpo`、`tech:scale_out_cpo`、`tech:silicon_photonics_chiplet`、
`tech:tfln_platform`、`tech:wdm_laser_16ch`、`tech:in_package_optical_io`、
`tech:dsp_1p6t`、`tech:serdes`。**層的名字有了，供應商一個都沒有。**

從 CPO stack 起手等於把一半已在那裡的骨架接完，能最快驗證這個機制會不會真的產出東西。

## 與其他 skill 的分工

| 情況 | 用哪個 |
|---|---|
| 在**已研究過的公司**裡排序 | `skills/alpha-status` pane 1（`rank_bottlenecks`） |
| 既有節點缺證據／缺供應商 | `skills/alpha-status` pane 2、3 |
| **產生圖裡沒有的新層** | **本 skill** |
| 拆解後某家公司要入圖 | `skills/company-onboard` |
| 拆解引用的文件要追一手 | `skills/source-trace` |
